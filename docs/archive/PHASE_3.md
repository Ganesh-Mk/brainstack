> script"** (4–6 days in the guide).

---

## 1. Goal & definition of done

**Goal:** understand embeddings, chunking, and retrieval *in your bones* — by
writing the cosine-similarity formula and the chunker yourself, watching them
work, and only then seeing that the industrial tools (LangChain, Pinecone) do
exactly the same thing at scale.

**Done when** (from the guide):

1. You can **explain embeddings to a friend without notes**.
2. The same query returns **the same top-5 chunks** from the hand-rolled
   version and from Pinecone — the "oh, it's the same thing" moment.
3. Every experiment in §6 has been run and its result written down.

### The hard rules of this phase

| Rule | Why |
|---|---|
| **No FastAPI** | Web plumbing is a distraction; it's already built and live. |
| **No frontend** | Not one page changes. Locked pages stay locked. |
| **No LangChain** *(until the very end)* | Write the chunker yourself first. |
| **No Pinecone** *(until the very end)* | Compute cosine similarity by hand over a plain list. Feel it. |
| **Cheap models only** | `claude-haiku-4-5` + a **free local** embedding model. |

> The whole point is to be **naked** first. Frameworks are added at the end,
> as a *comparison*, not as a starting point.

## 3. Where it lives — a separate `lab/` folder

```
brainstack/
├── backend/         ← untouched (stays lean — Render installs its requirements)
├── frontend/        ← untouched
├── docs/
└── lab/             ← NEW: the laboratory
    ├── requirements.txt      ← sentence-transformers, pymupdf, anthropic, numpy
    ├── data/
    │   └── handbook.pdf      ← generated sample company handbook (§4)
    ├── rag_lab.py            ← ⭐ the naked pipeline, hand-written
    ├── experiments.py        ← the §6 experiments, each printing its lesson
    ├── rag_framework.py      ← the same thing with LangChain + Pinecone
    ├── compare.py            ← proves hand-rolled top-5 == Pinecone top-5
    └── NOTES.md              ← what surprised us (guide principle #5)
```

**Why a separate folder + its own venv:** `sentence-transformers` pulls in
PyTorch (~hundreds of MB). Putting that in `backend/requirements.txt` would
bloat every Render deploy for code the API never runs. The lab stays local.

> ⚠️ **Install note:** the first `pip install` downloads PyTorch and the first
> run downloads the ~90 MB MiniLM model (once, cached). If PyTorch is painful
> on Windows, `fastembed` (ONNX, same model, much lighter) is the fallback —
> the lesson is identical.

## 4. The corpus — a realistic sample handbook

Retrieval experiments need a document with **distinct topics that use different
words for the same idea** (that's what makes semantic search visible).

We generate `lab/data/handbook.pdf` — a fictional **Lovely employee
handbook** (~8–10 pages) with clearly separated sections:

- Refunds & returns *(deliberately worded as "returns", so a query about
  "refund policy" must match on meaning, not keywords)*
- Leave & time off · Expenses & reimbursement · Security & device policy ·
  Onboarding · Support escalation & SLAs

It's generated by a script (reproducible, no copyright issues), and the
question set in §6 is written against its actual content.

---

## 5. Build order — the naked pipeline first

**Step 1 — `extract_pdf()`** — PyMuPDF, page by page, keeping page numbers.
*(Page numbers matter: they become citations in Phase 4.)*

**Step 2 — `split()` — written by hand.** A character/word-window chunker with
`size` and `overlap` parameters. No library. Understand why overlap exists by
*not* having it (§6.3).

**Step 3 — `embed()`** — `sentence-transformers` with `all-MiniLM-L6-v2`,
local and free. Print the vector: 384 floats. *That's what a "meaning" looks
like to a machine.*

**Step 4 — `store()`** — a plain JSON file: `[{id, text, page, vector}]`. A
vector database is a list plus an index; start with the list.

**Step 5 — `cosine_similarity()` — written by hand**, from the formula:
`dot(a,b) / (norm(a) * norm(b))`. Then `cosine_top_k()` — score every chunk,
sort, take k. **This is the entire retrieval engine.** It's about six lines.

**Step 6 — `build_prompt()` + `ask_claude()`** — stuff the top-k chunks into a
prompt with the question, call `claude-haiku-4-5`, print the answer.

At this point the full loop works: **PDF → chunks → vectors → cosine → Claude →
grounded answer**, with zero frameworks.

## 6. The experiments — where the learning actually happens

Each runs from `experiments.py`, prints real numbers, and its result gets
written into `NOTES.md`.

**6.1 — Does semantic search actually work?**
Cosine similarity between `"refund"` ↔ `"return policy"` ↔ `"the cat sat on
the mat"`.
*Expect:* refund/return score high despite sharing no words; the cat scores
near zero. **This is the moment embeddings click.**

**6.2 — Chunk size changes everything.**
Rebuild at **200 / 800 / 3000** characters; ask the same question at each.
*Expect:* 200 → precise but truncated context; 800 → the sweet spot; 3000 →
retrieval gets vague because one vector must represent too many ideas.

**6.3 — Why overlap exists.**
Set `overlap=0` and hunt for a question whose answer straddles a chunk
boundary — then watch it break, and watch overlap fix it.

**6.4 — Watch it hallucinate.**
Ask something absent from the handbook (e.g. "what's the parental leave
policy?" when the doc has none). *Expect:* a confident, fluent, **completely
invented** answer. This is the failure mode the whole product must prevent.

**6.5 — Grounding: the one-line fix.**
Add *"Answer only from the context below. If it isn't there, say you don't
know."* Re-run 6.4. *Expect:* it stops. **That single instruction is the
difference between a toy and a trustworthy product.**

**6.6 — Retrieval quality vs. answer quality.**
Take a question that returns *wrong* chunks and show the answer is wrong even
though the model is fine. *Lesson:* in RAG, **retrieval is the bottleneck** —
which is why the next phases invest in chunking, re-ranking, and evaluation.

## 7. Then — and only then — the frameworks

**`rag_framework.py`** redoes the exact same pipeline with:

- LangChain's `RecursiveCharacterTextSplitter` instead of our hand chunker —
  and we diff the chunk boundaries to see what it does smarter (splits on
  paragraph → sentence → word, rather than blindly at N characters).
- **Pinecone** instead of the JSON file — `upsert` into namespace `_lab`,
  `query` for top-5.

**`compare.py`** runs the same question through both and asserts the top-5
chunk IDs match. When they do, the point lands: **Pinecone is the
`cosine_top_k` you just wrote, at scale and behind a namespace.**

*(The `_lab` namespace is deliberately separate from the per-tenant namespaces
the product will use — no test data pollutes real tenants.)*

## 9. Cost

Roughly **30–60 Claude Haiku calls** across all experiments at ~1–2k tokens
each → **well under $1 total**. Embeddings are free (local). Pinecone usage is
a handful of vectors on the free tier.
