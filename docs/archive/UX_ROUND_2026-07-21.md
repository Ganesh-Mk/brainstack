## Multi-workspace (the big one)

The workspace dropdown used to show demo workspaces with a "real
multi-tenancy arrives with the backend" note — stale, and the "+ add"
didn't exist. Now it's real:

- `users.email` uniqueness moved from global to **(tenant_id, email)**
  (migration `9c41d7aa02be`). One person can hold a user row in many
  tenants.
- `GET /auth/workspaces` — every tenant where my email has a row, with my
  role there. `POST /auth/workspaces` — new tenant, me as admin, same
  credentials. `POST /auth/workspaces/{id}/switch` — a fresh token scoped
  to that tenant, through the same `_auth_response` path as login.
  **`get_current_user()` stays the only source of tenant/role** — switching
  changes which token you hold, never what a token means.
- Login now picks the newest row whose password matches; invites are
  scoped per-tenant (same email can be invited into a second workspace).
- Frontend: the Topbar switcher lists real workspaces; picking one (or
  creating one) swaps the session and does a full reload so **every page
  refetches inside the new workspace**.
- Trust model note: the platform has no email verification anywhere, so
  email == identity was already the rule; workspaces follow it.

## Connections "Not connected" (report #8) — a three-layer onion

1. First cut: a failed discovery was cached 30s, so Refresh re-served the
   failure. Fix: `/connections?refresh=true` busts the cache and pings the
   company `/health` first.
2. Still failed from cold. Instrumented the wake (`wake: {ok, detail, ms}`
   in the response — Render logs are user-only) and **measured the real
   cause: Render's edge returns an instant 502 to service-to-service
   requests aimed at a napping free-tier service, for the entire 60s
   budget. Spin-up only triggers for requests from OUTSIDE Render's
   network** (a browser or curl rides it in ~35s).
3. Final fix: `/connections` returns `wake_url` (the company's public
   /health URL); the **browser** fires a no-cors fetch at it — that's the
   external request that triggers spin-up — while the backend's looped
   ping (15s timeout / 3s gap / 60s budget) waits for the service to come
   up, then discovery lands.
